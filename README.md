# LOOM

A CRM where AI is part of the core workflow: every deal gets an explainable lead score, Claude drafts follow-ups from the deal history, meeting transcripts become summaries + tasks + sentiment, you can ask the pipeline questions in plain English, notes are searchable by meaning, likely duplicate contacts land in a review queue, and at-risk deals surface on the dashboard with a written reason.

**Stack:** Next.js 16 (App Router) + Tailwind v4 + shadcn/ui · Express 5 + Mongoose 9 · BullMQ (Redis) · Anthropic Claude (`@anthropic-ai/sdk`) · embeddings via Voyage / OpenAI / local ONNX model · vector store Pinecone or MongoDB.

## Quick start (zero configuration)

```bash
npm install
npm run dev
```

Open http://localhost:3000 and sign in as `admin@crm.dev` / `password123` (members: `ben@crm.dev`, `cara@crm.dev`).

With no environment variables the API boots an in-memory MongoDB, an in-process job queue, seeds demo data (17 contacts, 14 deals, notes, tasks, one call transcript, three planted duplicate pairs) and runs every AI feature in **fallback mode**. The first start downloads a MongoDB binary (~800 MB, cached) and a 23 MB sentence-embedding model.

### Turning on Claude

```bash
cp .env.example .env
# set ANTHROPIC_API_KEY=sk-ant-...
npm run dev
```

The header pill switches from "AI offline · fallback mode" to "Claude · claude-opus-5". Sentiment, drafts, summaries, NL queries, risk explanations and duplicate verdicts are now generated by the model; everything is logged under **Admin → AI usage**.

### Persistent infrastructure

```bash
docker compose up -d            # MongoDB 8 + Redis 7
# .env: MONGODB_URI=mongodb://localhost:27017/crm  REDIS_URL=redis://localhost:6379
npm run seed                    # seeds a persistent DB (add --reset to wipe)
npm run dev
```

With `REDIS_URL` set the queue adapter switches to BullMQ (durable jobs, retries with backoff, real cron schedules). With `PINECONE_API_KEY` + `PINECONE_INDEX` set, embeddings go to Pinecone instead of MongoDB.

## Accounts

There is no public sign-up. People join by invitation only, which is the right default for a
private sales tool.

**First run.** An instance with no accounts shows a one-time setup screen that creates the first
administrator. It is refused the moment any account exists, so it cannot be replayed. The demo
seed normally fills an empty database instead; set `SEED_ON_START=false` for a real deployment and
you will get the setup screen.

**Adding people.** An administrator invites from **Admin → Team**. The invitee gets a one-time link
and chooses their own password, so nobody else ever knows it. Links expire after seven days,
work once, and are cancelled by issuing a new one for the same address. With `SMTP_URL` set the
link is emailed; without it the app shows the link so you can pass it on yourself.

**Roles and safety rails.** Administrators can change roles and remove accounts. The app refuses to
strip the last administrator, to let you demote or delete yourself, or to remove anyone who still
owns records, so nothing is silently orphaned.

## Architecture

```
apps/web        Next.js UI. /api/* is rewritten to Express so auth cookies stay first-party.
apps/api        Express API, Mongoose models, AI features, background jobs.
packages/shared Zod request schemas, DTO types and the NL-query DSL + validator (used by both sides).
```

### Key decisions

**One AI gateway** (`apps/api/src/ai/gateway.ts`). Every LLM call goes through `callStructured()`, which enforces a per-call timeout plus a hard deadline, a circuit breaker (N consecutive failures → fail fast for a cool-down), a concurrency cap, a Mongo-backed response cache keyed on the prompt version + inputs, and writes one `AiUsage` row per call (tokens, cache reads, latency, estimated USD, status). Callers always receive a result object, never an exception, so an outage can only degrade a feature to its fallback.

**Structured outputs everywhere.** The Claude provider uses `output_config.format` with a Zod schema (`client.beta.messages.parse`), so responses are schema-validated JSON. Combined with the prompt-injection rules this means note content can never change the *shape* of what the model returns. Requests opt into server-side refusal fallbacks (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`; disable with `AI_SERVER_FALLBACKS=false`) and mark the system prompt as a prompt-cache breakpoint.

**Lead score is a transparent model, not an LLM guess.** `score = stagePrior + recency + value + stageVelocity + sentiment + engagement`, clamped to 0-100 and stored with a full breakdown that the UI shows on hover. Claude's contribution is the per-note sentiment (with a keyword lexicon as fallback). Re-scoring runs as a background job on every deal/note change and is keyed on an input hash, so unchanged deals are never recomputed. A nightly job refreshes recency.

**Natural-language queries never execute model output.** Claude returns a small typed DSL (`entity`, `filters[]`, `sort`, `limit`). The server validates it against a per-entity allowlist of fields, operators-per-type, a relative-date grammar, limits, and rejects `$`-prefixed keys, then compiles it to a read-only Mongo filter that always ANDs the member's ownership scope. Anything else (writes, aggregations, unrelated questions) is returned as `unsupported`. A small rule-based translator covers common questions when the model is unavailable.

**Queues, DB, embeddings and vector store are adapters.** `REDIS_URL` → BullMQ, otherwise an in-process queue with the same contract (job-id de-duplication, delays, repeatables). `MONGODB_URI` → your database, otherwise mongodb-memory-server. `EMBEDDINGS_PROVIDER=auto` picks Voyage → OpenAI → local `Xenova/all-MiniLM-L6-v2` (runs in-process, no key). Vector search falls back to MongoDB text search whenever the provider or store is unavailable, and the response says which mode ran.

**Prompt-injection hardening** (`ai/sanitize.ts`): all user-supplied text is NFKC-normalised, stripped of control/zero-width characters, has angle brackets neutralised (so it cannot close the `<data>` delimiters), is length-capped, and is wrapped in `<data type=…>` blocks. Every system prompt carries explicit rules that `<data>` content is untrusted and never instructions. Notes that look like injection attempts are flagged (`suspicious`) for humans, never blocked.

**Never auto-merge, never auto-send.** Duplicate candidates are generated deterministically (email edit distance, phone normalisation, name similarity with nicknames/order/typos, company match) and optionally adjudicated by Claude; an admin chooses the survivor. Email drafts are editable and only logged as a timeline note when the user clicks send (SMTP delivery is optional via `SMTP_URL`).

### AI features and their fallbacks

| Feature | With Claude | Without Claude / on failure |
|---|---|---|
| Lead scoring | Sentiment per note classified by Claude, cached 30 days | Keyword lexicon sentiment; score model unchanged |
| Email drafting | Personalised draft from contact, deal, last 8 notes, open tasks, latest meeting summary | Stage-based template, clearly labelled |
| Ask your CRM | Question → validated DSL → table | Rule-based translator for common questions; otherwise a clear "unavailable" |
| Assistant | Adds contacts, deals, tasks and notes, moves deals, opens records, explains the product | Questions still answered by the rule-based translator; changes need a model |
| Meeting summary | Summary, action items (→ tasks), sentiment (→ score), next steps, topics | Extractive summary + commitment-phrase action items, labelled "basic extraction" |
| Semantic search | Embeddings (Voyage / OpenAI / local) + vector store | MongoDB `$text` search, response says `mode: "text"` and why |
| Duplicate detection | Rule-based candidates + Claude verdict with reason | Rule-based candidates only |
| Risk flagging | Rule signals + Claude-written reason and suggested action | Rule signals with templated reason |

### Background jobs

`deal.score`, `contact.score`, `note.enrich` (sentiment + embedding + rescore), `meeting.summarize`, `contact.dedupe`, `deal.risk`, and scheduled `risk.scan` (daily, `RISK_SCAN_CRON`), `score.scanAll` (05:00) and `dedupe.scanAll` (05:30). Rapid edits to the same record coalesce into one job.

### Security & limits

- JWT in an httpOnly cookie; `admin` sees everything, `member` only records they own (enforced in every query, including NL queries and semantic search).
- Per-user rate limit on AI endpoints (`AI_RATE_LIMIT_PER_MINUTE`), login rate limit, Helmet, 2 MB body limit, Zod validation on every input.
- The local vector store ranks with in-process cosine similarity; fine for tens of thousands of notes, use Pinecone beyond that.
- Merges are not transactional (sequential updates); the in-memory queue is not durable. Both are production-grade with Redis + a replica-set MongoDB.

## Performance

Measured with `npm run bench -w @loom/api`, which loads a synthetic dataset into a throwaway
database and times the paths that grow super-linearly. At 2,000 contacts / 6,000 notes:

| Path | Before | After | Change |
|---|---|---|---|
| Duplicate scan (1,200 contacts) | 7,438 ms | 140 ms | **53× faster** |
| Vector load (6,000 embeddings) | 164 ms | 36 ms | **4.6× faster** |

**Duplicate detection was O(n²).** Every contact was compared against every other, which is
719k comparisons at 1,200 contacts and roughly 8.6 minutes of CPU at 10,000. It now generates
candidates from blocking keys (email local part, domain + surname, phone suffix, surname +
company, initial + surname, sorted name tokens) and only scores pairs that share one. That is
1.5% of the cross join, and a key shared by more than 60 records is skipped so a large employer
cannot reintroduce the blow-up. All five realistic duplicate classes are still caught, which
`duplicates.test.ts` locks in.

**Vector search spent its time loading, not comparing** (164 ms of read against 6 ms of
arithmetic). Vectors are now stored as packed Float32 rather than arrays of BSON doubles, halving
the bytes and skipping per-element decode, L2-normalised on write so ranking is a dot product,
and cached in process with invalidation on write. Rows written by an earlier version still load.

Beyond roughly 100k notes, move vectors out of the database by setting `PINECONE_API_KEY`.

### Known remaining limits

- Deep pagination uses skip/limit, which slows as the offset grows. Fine to a few thousand rows per owner; use a cursor beyond that.
- Deal search by contact or company runs an unindexed regex over contacts, then an `$in`. Add a text index or a denormalised company field if contact counts get large.
- The dashboard, deal list and deal detail poll on an interval. Cheap here; switch to server-sent events if you scale the number of open tabs.

## Deployment

Both halves run on Vercel as two projects from this repository: the Next.js app, and the
Express API as a serverless function. Next rewrites `/api/*` to the API server-side, so the
browser sees one origin and the session cookie stays first-party.

Running serverless changes three things, and the app detects the host and adapts: background
jobs run on the request path instead of a worker, the nightly scans become one daily cron,
and semantic search needs a hosted embedding key rather than the local model. Full detail,
including every environment variable and how to get the original behaviour back, is in
[DEPLOY.md](DEPLOY.md). [`Dockerfile`](Dockerfile) and [`render.yaml`](render.yaml) describe
the same API on a host with a real process.
